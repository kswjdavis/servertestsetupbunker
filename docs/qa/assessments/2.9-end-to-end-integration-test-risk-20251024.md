## Critical Risks Requiring Immediate Attention

### 1. TECH-001: SQLite vs PostgreSQL Dialect Differences

**Score: 9 (Critical)**
**Probability:** High (3) - Test uses different database than production
**Impact:** High (3) - Production-specific SQL may not work as expected

#### Description
The test suite uses SQLite in-memory database (`conftest.py:26`), but production uses PostgreSQL. The `DeviceStatusRepository.upsert_status` method uses PostgreSQL-specific syntax:

```python
# device_status_repository.py:71-81
stmt = stmt.on_conflict_do_update(
    index_elements=["device_id"],
    set_={...}
)
```

SQLite's `ON CONFLICT` syntax differs from PostgreSQL's, and SQLAlchemy's dialect handling may not catch all edge cases. This is particularly risky because:
- Upsert is called 60 times in the test (line 151 of test file)
- Production will use this heavily (every device status report)
- Foreign key cascade behavior differs between SQLite and PostgreSQL

#### Evidence Locations
- `server/tests/conftest.py:26` - `TEST_DATABASE_URL = "sqlite+aiosqlite:///:memory:"`
- `server/app/repositories/device_status_repository.py:71-81` - PostgreSQL `on_conflict_do_update`
- `server/tests/test_end_to_end_integration.py:174` - Assumes upsert works correctly

#### Mitigation Actions
**MUST FIX before hardware handoff:**
1. Add PostgreSQL-specific integration test that runs against a real PostgreSQL database
2. Use testcontainers-postgres or docker-compose test database for integration tests
3. Keep SQLite tests for unit tests, but validate PostgreSQL behavior in integration suite
4. Add test that verifies upsert behavior with multiple rapid updates (race condition testing)

**Implementation Steps:**
```bash
# Add to docker-compose.test.yml
services:
  postgres-test:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: test_bunkercolab
      POSTGRES_USER: test_user
      POSTGRES_PASSWORD: test_pass
```

**Testing Requirements:**
- Run integration test against PostgreSQL container
- Verify all 60 upserts succeed without errors
- Check final database state matches expected values
- Validate constraint enforcement (CHECK constraints on countdown_timer_remaining)

**Residual Risk:** Low - PostgreSQL containers are reliable for testing
**Owner:** Dev
**Timeline:** Before hardware handoff

### 2. DATA-001: Weather Service Staleness Not Tested

**Score: 9 (Critical)**
**Probability:** High (3) - Real ESP32 will definitely encounter stale weather
**Impact:** High (3) - Could cause incorrect shutdown decisions affecting grain safety

#### Description
The weather service has staleness detection (`weather_service.py:138-142`), and the control logic falls back to safe mode when weather is unavailable (`control_logic_engine.py:98-101`). However, the integration test never validates this critical fail-safe path:

```python
# control_logic_engine.py:98-101
try:
    weather = weather_service.get_current_weather()
except ValueError as exc:
    logger.warning("Weather data unavailable: %s", exc)
    return False  # Fail-safe: disallow shutdown
```

The test stubs weather data (`test_end_to_end_integration.py:19-46`) but never tests:
- What happens when `cached_weather = None`
- What happens when `last_successful_fetch` exceeds stale threshold
- Whether control logic correctly defaults to "fans ON" when weather is stale
- ESP32 behavior when receiving `reason: "default_safe"` due to stale weather

#### Evidence Locations
- `server/app/services/weather_service.py:115-136` - `get_current_weather()` staleness logic
- `server/app/services/weather_service.py:138-142` - `is_weather_stale()` method
- `server/app/services/control_logic_engine.py:98-101` - Fail-safe on weather unavailable
- `server/tests/test_end_to_end_integration.py:43` - Weather always valid in test

#### Mitigation Actions
**MUST FIX before hardware handoff:**
1. Add test scenario where weather becomes stale mid-test
2. Verify control logic returns `shutdown_allowed=False, reason="default_safe"`
3. Add test for weather service raising `ValueError` when no cache exists
4. Document expected ESP32 behavior when weather staleness triggers fail-safe

**Implementation Steps:**
```python
# Add to test_end_to_end_integration.py or new test file
async def test_stale_weather_triggers_fail_safe(client, weather_stub):
    # Set up device and bunker
    # ...

    # Report status with valid weather
    response1 = await client.post("/api/v1/control/status", ...)
    assert response1.json()["shutdown_allowed"] is True

    # Simulate weather staleness by setting last_fetch to old time
    from app.services.weather_service import weather_service
    weather_service.last_successful_fetch = datetime.now(timezone.utc) - timedelta(hours=2)

    # Next status report should fail-safe
    response2 = await client.post("/api/v1/control/status", ...)
    assert response2.json()["shutdown_allowed"] is False
    assert response2.json()["reset_countdown"] is False
    # Reason might be "default_safe" or could add specific "weather_stale" reason
```

**Testing Requirements:**
- Test weather staleness detection at exact threshold boundary
- Test control logic behavior when `get_current_weather()` raises `ValueError`
- Verify staleness warning is logged
- Test recovery when weather becomes fresh again

**Residual Risk:** Low - Clear fail-safe behavior coded
**Owner:** Dev
**Timeline:** Before hardware handoff

## High Risks Requiring Mitigation

### 3. TECH-002: Real-Time Timing Assumptions

**Score: 6 (High)**
**Probability:** Medium (2) - Hardware will have actual timing constraints
**Impact:** High (3) - Dead-man timer is safety-critical

#### Description
The test simulates 60 minutes of operation by executing 60 status reports in a tight loop (`test_end_to_end_integration.py:126-183`). This doesn't validate:
- Countdown timer decrement behavior over real 60-second intervals
- Edge cases like status report arriving at second 59 of 300-second countdown
- Clock drift between ESP32 and server
- What happens if status report is delayed beyond 60 seconds

The test uses `uptime_seconds=(minute + 1) * 60` (line 146), but this is simulated time, not real elapsed time. The `countdown_timer_remaining` is hardcoded as `max(0, 300 - minute * 5)` (line 147), which doesn't reflect actual ESP32 countdown behavior.

#### Mitigation
**SHOULD FIX or document as known limitation:**
1. Add test with actual time delays using `asyncio.sleep()` for at least 2-3 status cycles
2. Document ESP32 countdown timer requirements clearly for firmware developer
3. Create sequence diagram showing expected timing: status report → server response → countdown reset → countdown decrement
4. Add test for "late status report" scenario (report arrives after >60s)

**Compensating Control:**
- Story 2.1 (Dead Man Timer) presumably has firmware-level tests
- Document that integration test validates control flow, not real-time behavior
- Plan hardware acceptance test that runs for actual 1 hour minimum

**Residual Risk:** Medium - Timing bugs may only appear on hardware
**Owner:** Dev (document), then hardware tester
**Timeline:** Document before handoff, validate during hardware testing

### 4. TECH-003: Concurrent Device Handling Not Tested

**Score: 6 (High)**
**Probability:** Medium (2) - Production will have multiple devices
**Impact:** High (3) - Database race conditions could cause incorrect state

#### Description
The integration test only provisions and tests a single device. Production will have multiple ESP32 controllers (potentially one per fan, per bunker). The `upsert_status` operation may have race conditions if multiple devices update simultaneously:

```python
# device_status_repository.py:71-92
stmt = stmt.on_conflict_do_update(...)
await self.session.execute(stmt)
await self.session.commit()
result = await self.session.execute(select(DeviceStatus)...)
```

If two devices call `/api/v1/control/status` simultaneously:
- Could cause deadlocks if both try to update same bunker's config
- Weather service cache is shared (singleton) - thread safety not validated
- Global config fetching (`control_logic_engine.py:117`) might cause lock contention

#### Mitigation
**SHOULD FIX or accept as known risk:**
1. Add test with 10+ concurrent devices sending status updates
2. Use `asyncio.gather()` to simulate parallel requests
3. Validate no database deadlocks occur
4. Check that all devices get correct, independent shutdown decisions
5. Consider adding database-level advisory locks if contention is high

**Alternative Approach:**
- Document that devices reporting at different seconds (0-59) naturally distributes load
- Accept that brief lock contention is acceptable for POC scale (10-20 devices)
- Monitor in production with logging

**Residual Risk:** Medium - Lock contention unlikely at POC scale
**Owner:** Dev (test) or accept risk with monitoring
**Timeline:** Optional before handoff, monitor in production

### 5. SEC-001: Device Token Reuse and Rotation

**Score: 6 (High)**
**Probability:** Medium (2) - No token lifecycle management exists
**Impact:** High (3) - Compromised token remains valid indefinitely

#### Description
Device authentication uses UUID tokens that never expire (`device.auth_token`). Unlike user JWT tokens (which have `ACCESS_TOKEN_EXPIRE_HOURS`), device tokens are permanent:

```python
# server/app/core/security.py:43-63
async def get_device_token(...) -> UUID:
    return UUID(credentials.credentials)  # No expiration check
```

If a device is decommissioned, stolen, or compromised:
- Token remains valid forever
- No mechanism to revoke a specific device token
- No rotation policy

The test provisions a device (`test_end_to_end_integration.py:108-114`) and uses the token 60 times, but never tests revocation, rotation, or token invalidation.

#### Mitigation
**SHOULD DOCUMENT as known limitation for POC:**
1. Add revocation endpoint: `DELETE /api/v1/devices/{device_id}/revoke`
2. Implement revoked tokens table (may already exist: `revoked_token_repository.py`)
3. Add token refresh mechanism for long-running devices
4. Document manual revocation procedure for compromised devices

**POC Acceptance Criteria:**
- Document that device tokens are permanent in POC
- Provide admin procedure to delete device record (cascades to invalidate token)
- Plan token rotation for production v2

**Residual Risk:** Medium - Physical device security is primary concern
**Owner:** Product (accept for POC) or Dev (implement revocation)
**Timeline:** Document before handoff, plan for production

## Medium Risks (Monitor During Hardware Testing)

### 6. TECH-004: Network Protocol Differences

**Score: 4 (Medium)**
**Probability:** Medium (2) - Test bypasses real HTTP
**Impact:** Medium (2) - Connection behavior differs

The test uses `AsyncClient` with `ASGITransport` (`conftest.py:66-69`), which bypasses actual HTTP/TLS networking. Real ESP32 will use HTTPS with:
- Certificate validation (FR15 in PRD)
- Connection pooling
- TCP timeout behavior
- Retry logic on transient failures

**Mitigation:** Document as expected difference; hardware testing will validate real HTTP behavior

### 8. PERF-001: Database Query Efficiency

**Score: 3 (Low-Medium)**
**Probability:** Low (1) - Likely fine at POC scale
**Impact:** High (3) - Could degrade with many devices

Each status update triggers 5+ queries:
1. Device lookup (`control.py:41`)
2. Device update for `last_seen` (`control.py:42`)
3. Upsert device_status (`control.py:48`)
4. Device lookup in control logic (`control_logic_engine.py:40`)
5. Bunker lookup (`control_logic_engine.py:44`)
6. Global config fetch (`control_logic_engine.py:48`)

With 100 devices @ 60s intervals = 500 queries/minute = 30,000 queries/hour

**Mitigation:** Accept for POC; monitor query performance in production
