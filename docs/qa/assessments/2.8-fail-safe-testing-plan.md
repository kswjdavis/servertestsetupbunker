# Story 2.8 – Fail-Safe Behaviour Test Plan

## Objective
Validate that every critical failure mode forces bunker fans into the ON state within the required timing so the system always flows to the safest outcome.

## Scope & Preconditions
- Firmware: `firmware/main` @ commit under test with `FIRMWARE_VERSION` reported in logs.
- Hardware: Provisioned ESP32 device wired to normally-closed relay driving fans (or bench supply with indicator LED).
- Backend: FastAPI server + PostgreSQL stack from monorepo (`docker-compose` recommended) with device already provisioned.
- Tooling: Serial console (`idf.py -p <port> monitor`), ability to toggle WiFi/Power, and access to droplet or local backend host.

## Instrumentation & Logging
- Start firmware monitor: `idf.py -p <port> monitor | tee logs/fail-safe-$(date -u +%Y%m%dT%H%M%SZ).log`
- Run backend + DB with structured logs enabled: `docker compose up server db`
- Enable API request logging (FastAPI `uvicorn --log-level info` already default).
- Capture manual actions & observations in the results table below; include UTC timestamps.
- After each scenario, snapshot relay state (`relay_get_state logs`) and, if possible, measure fan voltage (>= line voltage implies ON).

## Detailed Procedures

### 1. WiFi Disconnect → Fans ON within 5 minutes
1. Ensure fans are currently OFF (`relay_get_state` reports `OFF`) and dead-man timer counts down from 300.
2. Cut network connectivity (power off AP or change SSID so reconnect fails).
3. Observe firmware log: WiFi disconnect warnings followed by countdown reaching zero.
4. Confirm relay locks ON (`RELAY LOCKED IN ON STATE` log). Record timestamp.
5. Restore WiFi and verify device stays in fail-safe until manual reset.

### 2. Server Shutdown → Fans ON within 5 minutes
1. Start with WiFi connected and backend responding.
2. Stop FastAPI process (`docker compose stop server`).
3. Watch firmware status reports fail (`Failed to report status`) and countdown expire.
4. Verify relay locks ON within 5 minutes; capture logs showing dead-man expiry.
5. Restart server; confirm device remains in fail-safe lock.

### 3. Invalid Authentication Token → Immediate Fail-Safe
1. With fans OFF, erase or corrupt auth token: `idf.py -p <port> erase_flash --partition auth_token` or `nvs_storage_clear_auth_token`.
2. Reboot device; status task detects missing/invalid token.
3. Confirm logs show `Authentication failure` and `Entering fail-safe mode` with no delay.
4. Check relay state (must be ON and locked).

### 4. ESP32 Crash → Watchdog Reboot Forces Fans ON
1. Enable test firmware flag to suspend watchdog feeding (set `TEST_DISABLE_WATCHDOG_FEED=1` if available or comment call temporarily).
2. Allow watchdog timeout; observe reboot.
3. On boot, confirm log `Watchdog reboot detected - relay reinitialized to fail-safe ON state`.
4. Verify fans physically ON during reboot window.

### 5. Power Cycle → Fans Initialize ON
1. With fans OFF, toggle device power.
2. Observe startup log `Relay controller initialized (...) Fail-safe default: fans ON`.
3. Confirm fans are ON before any network communication occurs.

### 6. Backend Crash During Call → Fail-Safe in ≤5 Minutes
1. Start `tcpdump` or similar to confirm outgoing request.
2. During status POST, kill backend (`pkill -9 uvicorn`).
3. Firmware should log connection failure; dead-man timer continues decrement.
4. Verify relay locks ON within 5 minutes; capture log evidence.

### 7. Database Connection Loss → Backend Defaults Fail-Safe
1. With backend running, stop PostgreSQL (`docker compose stop db`) while server remains up.
2. Send status POST (manually via `curl` with device token or allow device report).
3. Observe backend log for database error handling and returned payload.
4. Confirm API response still sets `shutdown_allowed=false` and `reset_countdown=false`.
5. Resume DB, ensure normal operation resumes.

## Automation Hooks
- Run host-based verification for firmware fail-safe primitives:
  ```bash
  cd firmware/tests
  make run
  ```
  Confirms dead-man timer expiry and relay lock semantics align with fail-safe requirements.
- The helper script `firmware/tests/run_fail_safe_matrix.sh` captures the full host simulation output with timestamped log files under `firmware/tests/logs/`.
- Host auth failure coverage: `firmware/tests/test_auth_fail_safe` (included in `make run`) verifies the new latch module forces the relay ON immediately.
- Backend fail-safe coverage: `PYTHONPATH=server python3 -m pytest tests/test_fail_safe_behaviour.py` (requires Python 3.10+) simulates database outages to confirm the API returns fail-safe decisions.
- Capture output and attach to evidence when updating results table.
