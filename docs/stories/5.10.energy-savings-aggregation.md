## Status

## Story
As a system administrator,
I want accurate energy savings and cost savings aggregated across all bunkers and devices,
so that I can quantify efficiency gains from the control logic and report operational ROI.

## Acceptance Criteria

1. System Health endpoint reports non-zero `total_energy_saved_kwh` when savings exist
2. Savings computed from measured device runtime vs. baseline power usage
3. Cost savings reported via `total_energy_cost_saved_usd = kWh_saved × default_electricity_cost_kwh`
4. Supports time windows: last 24h and lifetime; System Health returns lifetime (retain windowed API surface for future)
5. Handles missing data gracefully (returns 0 with reason message in logs)
6. Includes unit tests covering: no data → 0, partial data, multi-bunker aggregation, rounding rules
7. No external dependencies; uses existing models/repos and adds a minimal runtime log model if required

## Dev Notes

### Proposed Data Model
`DeviceRuntimeLog`
- device_id (UUID)
- started_at (timestamptz)
- ended_at (timestamptz)
- state (enum: on, off)
- source (enum: control_logic, manual, emergency)
- created_at/updated_at

Rationale: Interval-based logs allow precise aggregation and later extension for detailed analytics.

### Aggregation Strategy
- Define a “baseline” as the counterfactual runtime without energy-saving control (e.g., duty cycle = 100% during applicable windows)
- Energy saved = baseline_runtime_seconds − actual_runtime_seconds, clamped to ≥ 0
- Power from `bunker.fan_power_watts` (fallback: `global_config.default_fan_power_watts`)
- kWh saved = (power_watts × seconds_saved / 3600) / 1000
- Cost saved = kWh_saved × `default_electricity_cost_kwh`
- Lifetime and rolling window (24h) queries supported by repository methods

### API Contracts
- No API change required for the dashboard; `SystemHealthSummary` already exposes
  `total_energy_saved_kwh` and `total_energy_cost_saved_usd`
