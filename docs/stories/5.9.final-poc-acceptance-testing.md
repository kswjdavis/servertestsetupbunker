### Testing Strategy Overview

The project follows a simplified testing pyramid for POC scope:
[Source: architecture.md#Testing Strategy]

**Testing Levels:**
- **Backend Unit Tests:** pytest-based automated tests in `server/tests/`
  - Test files: `test_auth.py`, `test_control_logic.py`, `test_energy_calculation.py`, `test_repositories.py`, `test_api/`
- **Frontend Tests:** Manual testing for POC (no automated UI tests required)
- **ESP32 Firmware Tests:** ESP-IDF unit testing framework for critical firmware logic
- **Integration Tests:** Manual end-to-end testing scenarios
- **E2E Tests:** Manual testing workflows (defined in Acceptance Test Scenarios section)

### Critical E2E Test Scenarios

These scenarios must pass for acceptance:
[Source: architecture.md#Testing Strategy - Manual E2E Test Scenario]

1. **Device Provisioning Flow:**
   - Create bunker via Web UI
   - Provision ESP32 device
   - Copy auth token to ESP32
   - Verify device appears online in Web UI

2. **Normal Operation:**
   - Monitor weather data updates (60s intervals)
   - Observe fan status changes based on wind
   - Verify energy savings calculations

3. **Emergency Scenarios:**
   - Trigger emergency ON from Web UI
   - Verify all fans activate within 60 seconds
   - Disconnect WiFi from ESP32
   - Verify fail-safe activates (dead-man timer expires → fans ON)

### Fail-Safe Behavior Requirements

All fail-safe mechanisms must be verified:
[Source: architecture.md#High Level Architecture]

- **Dead-Man Timer:** ESP32 devices must activate fans ON when server communication is lost for 5 minutes
- **WiFi Loss:** Fans default to ON state when WiFi connectivity is lost
- **Server Failure:** System degrades gracefully; edge devices maintain fail-safe operation
- **Emergency ON Mode:** All fans must respond within 60 seconds to emergency commands

**Testing Framework:**
- **Backend:** pytest 7.x+ with async support for FastAPI testing
- **Frontend:** Manual testing (no automated framework for POC)
- **E2E:** Manual testing scenarios following acceptance test scenarios
- **Firmware:** ESP-IDF unit testing framework for critical safety logic

**Test Coverage Requirements for POC:**
- All safety-critical firmware logic (dead-man timer, watchdog, fail-safe) must have unit tests
- Backend API endpoints should have basic functional tests
- UI and integration workflows verified through manual testing
- Focus on correctness over comprehensive coverage

## Acceptance Test Scenarios

### Scenario 1: Complete Device Lifecycle
1. Create bunker via Web UI
2. Provision device via Web UI
3. Flash firmware to ESP32 with auth token
4. Verify device connects and authenticates
5. Monitor status reports for 1 hour
6. Verify energy savings calculations
7. Deprovision device

### Scenario 2: Fail-Safe Verification
1. Device operating normally (fans cycling)
2. Disconnect WiFi from ESP32
3. Verify dead-man timer expires (5 min)
4. Verify fans turn ON
5. Reconnect WiFi
6. Verify system recovers

### Scenario 3: Emergency Response
1. Multiple devices online, some fans OFF
2. Operator clicks "Emergency ON All"
3. Verify all fans turn ON within 60 seconds
4. Clear emergency mode
5. Verify normal operation resumes

### Scenario 4: Configuration Management
1. Change global wind threshold
2. Verify new threshold applied to decisions
3. Add time window override
4. Verify fans stay ON during window
5. Delete override
6. Verify normal operation resumes
