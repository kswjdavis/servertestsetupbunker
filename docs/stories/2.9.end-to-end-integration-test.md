### Critical Blockers (MUST FIX Before Hardware Handoff)

#### 1. TECH-001: SQLite vs PostgreSQL Dialect Differences ⚠️ CRITICAL
**Location:** `server/tests/conftest.py:26`, `server/app/repositories/device_status_repository.py:71`

**Issue:** Test suite uses SQLite in-memory database, but production uses PostgreSQL. The `DeviceStatusRepository.upsert_status` method uses PostgreSQL-specific `on_conflict_do_update` syntax that may behave differently on SQLite. The integration test calls this upsert 60 times without validating PostgreSQL-specific behavior.

**Required Fix:**
- Add PostgreSQL integration test using testcontainers-postgres or docker-compose test database
- Validate all 60 upserts complete successfully against real PostgreSQL 16
- Verify constraint enforcement and foreign key cascade behavior
- Keep SQLite tests for unit tests, but validate PostgreSQL for integration

**Estimated Effort:** 2-3 hours

---

#### 2. DATA-001: Weather Service Staleness Not Tested ⚠️ CRITICAL
**Location:** `server/app/services/weather_service.py:138`, `server/app/services/control_logic_engine.py:98`

**Issue:** Weather service has staleness detection and control logic has fail-safe fallback when weather unavailable, but integration test never validates this critical safety path. Real ESP32 will definitely encounter stale weather data. Test stubs weather but never tests `cached_weather = None` or `last_successful_fetch` exceeding stale threshold.

**Required Fix:**
```python
# Add test scenario
async def test_stale_weather_triggers_fail_safe(client, weather_stub):
    # ... setup device and bunker
    # Simulate staleness
    weather_service.last_successful_fetch = datetime.now(timezone.utc) - timedelta(hours=2)
    # Verify fail-safe
    response = await client.post("/api/v1/control/status", ...)
    assert response.json()["shutdown_allowed"] is False
    assert response.json()["reason"] == "default_safe"
```

**Estimated Effort:** 1 hour

### High Priority Concerns (Address or Document)

#### 3. TECH-002: Real-Time Timing Assumptions
**Severity:** High | **Impact:** Dead-man timer is safety-critical

Test simulates 60 minutes by executing 60 status reports in tight loop (`test_end_to_end_integration.py:126`). Doesn't validate countdown timer behavior over real 60-second intervals, clock drift, or late status reports.

**Recommendation:** Document countdown timer requirements clearly for ESP32 developer with sequence diagram. Add optional real-time test with `asyncio.sleep(60)` for 2-3 cycles. Plan hardware acceptance test that runs actual 1 hour minimum.

---

#### 4. TECH-003: Concurrent Device Handling Not Tested
**Severity:** High | **Impact:** Database race conditions possible

Test only provisions single device. Production will have multiple ESP32s. Upsert operations, weather cache access, and config lookups may have race conditions with concurrent requests.

**Recommendation:** Add test with 10+ devices using `asyncio.gather()` OR document as POC limitation (max 20 devices) and monitor in production.

---

#### 5. SEC-001: Device Token Never Expires
**Severity:** High | **Impact:** Compromised token valid indefinitely

Device authentication uses UUID tokens without expiration (unlike user JWT with `ACCESS_TOKEN_EXPIRE_HOURS`). No revocation or rotation mechanism exists.

**Recommendation:** Document token lifecycle in architecture. Provide admin procedure for device decommissioning (delete device record). Plan token rotation for production.
