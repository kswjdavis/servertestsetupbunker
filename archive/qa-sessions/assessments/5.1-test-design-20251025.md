# Test Design: Story 5.1 - LED Flash Identification System

**Date:** October 25, 2025
**Designer:** Quinn (Test Architect)
**Story:** 5.1 - LED Flash Identification System (ESP32)
**Epic:** Epic 5 - Field Deployment Support

---

## Test Strategy Overview

- **Total test scenarios:** 23
- **Unit tests:** 8 (35%)
- **Integration tests:** 10 (43%)
- **Hardware/E2E tests:** 5 (22%)
- **Priority distribution:** P0: 8, P1: 11, P2: 4

### Test Level Rationale

This firmware feature requires a balanced approach:
- **Unit tests** for GPIO initialization, input validation, and state management
- **Integration tests** for FreeRTOS task behavior, NVS interaction, and WiFi event handling
- **Hardware tests** for actual LED flash pattern validation and timing verification

### Risk-Based Focus Areas

1. **Timing accuracy** - 200ms ON/OFF must be precise for visual identification
2. **Task isolation** - FreeRTOS task must not interfere with dead-man timer or HTTP client
3. **Flash sequence correctness** - Operators depend on correct pattern matching
4. **Hardware variability** - Different ESP32 models may have different GPIO pins

## Recommended Execution Order

### Phase 1: Fast Feedback (Unit Tests)
**Execute first** to catch basic logic errors early:
1. 5.1-UNIT-001 (P0) - Validate flash_count range
2. 5.1-UNIT-002 (P0) - Reject invalid flash_count
3. 5.1-UNIT-003 to 5.1-UNIT-008 (P1/P2) - Configuration validation

**Estimated time:** < 5 minutes

---

### Phase 2: Integration Validation
**Execute second** to verify component interactions:
1. **P0 Integration Tests** (Critical path):
   - 5.1-INT-004 - Task creation
   - 5.1-INT-005 - Task running
   - 5.1-INT-009 - WiFi event handling
   - 5.1-INT-011 - Dead-man timer non-interference
   - 5.1-INT-012 - HTTP client non-interference

2. **P1 Integration Tests** (Core functionality):
   - 5.1-INT-001 - NVS read
   - 5.1-INT-002 - Task loop sequence
   - 5.1-INT-003 - GPIO toggle timing
   - 5.1-INT-006 - Task handle storage
   - 5.1-INT-007 - Task cleanup
   - 5.1-INT-010 - WiFi timing guard
   - 5.1-INT-013 - Provision API response

3. **P2 Integration Tests** (Configuration):
   - 5.1-INT-008 - Custom GPIO via menuconfig

**Estimated time:** 15-30 minutes (depends on hardware setup)

---

### Phase 3: Hardware Validation
**Execute third** to validate actual LED behavior:
1. **P0 Hardware Tests** (Must pass before deployment):
   - 5.1-HW-001 - Flash pattern matching
   - 5.1-HW-002 - 2-second pause timing

2. **P1/P2 Hardware Tests** (Should pass):
   - 5.1-HW-004 - Long-term stability
   - 5.1-HW-005 - Custom GPIO portability

**Estimated time:** 30-60 minutes (includes oscilloscope measurements)

### Phase 4: End-to-End Validation
**Execute last** to validate complete workflows:

   - 5.1-E2E-001 - Boot → WiFi → LED workflow

## Test Implementation Notes

### Unit Test Framework
**Recommendation:** ESP-IDF Unity framework
```c
// Example unit test structure
TEST_CASE("LED controller validates flash_count range", "[led_controller]")
{
    TEST_ASSERT_EQUAL(ESP_OK, led_flash_task_start(1));
    TEST_ASSERT_EQUAL(ESP_OK, led_flash_task_start(10));
    TEST_ASSERT_EQUAL(ESP_FAIL, led_flash_task_start(0));
    TEST_ASSERT_EQUAL(ESP_FAIL, led_flash_task_start(11));
}
```

### Integration Test Setup
**Requirements:**
- ESP32 hardware with WiFi credentials configured
- Test NVS partition with known led_flash_sequence values
- Monitor output for task creation logs
- Dead-man timer and HTTP client running concurrently

### Hardware Test Equipment
**Required:**
- ESP32-DevKitC (or target hardware)
- Oscilloscope or logic analyzer (for timing measurements)
- Timer/stopwatch (for visual validation)
- Multimeter (optional - for GPIO voltage verification)

### E2E Test Environment
**Components:**
- Production backend with test database
- Web UI (for provisioning workflow)
- ESP32 hardware
- Network access

### Optional Enhancements

1. **Stress Testing** (P3):
   - Test LED task under memory pressure
   - Test with multiple WiFi reconnection cycles
   - Test with OTA update in progress

2. **Edge Cases** (P2):
   - Test GPIO initialization failure handling
   - Test NVS corruption recovery
   - Test LED task with extremely low CPU clock speed

3. **Portability** (P2):
   - Test on ESP32-S3, ESP32-C3 variants
   - Test with different LED polarities (active-high vs active-low)
